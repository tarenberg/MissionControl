**Process Management Instability (Frontend & Backend Node.js Servers):**
- **Problem:** Node.js backend (`server.js`) and React frontend (`vite`) development servers, when managed by OpenClaw's `exec` (even with `pty: true`), are highly unstable, frequently terminating unexpectedly (`signal SIGKILL`) or failing to start reliably. This has caused significant delays and "Failed to fetch" errors.
- **Root Cause Identified:** OpenClaw's direct `exec` management of these specific Node.js processes in your environment is unreliable.
- **Action Taken:** Transitioned to **manual process management** for both backend and frontend servers. User is now responsible for starting and keeping these servers running in dedicated terminal windows.
- **Current Status:** Process stability is now externalized and appears resolved under manual user control.

### Lessons Learned:
- **`openclaw sessions --json` Output Variability:** Do not assume explicit status fields (`endedAt`, `paused`, `error`, `pending`) will always be present in `openclaw sessions --json` output. Be prepared to derive statuses heuristically from available fields like `updatedAt`, `ageMs`, `abortedLastRun`.
- **Tool Deprecation & Version Awareness:** Always verify tool configurations against the user's specific OpenClaw version, especially for features like "browser relay" that might be deprecated. My failure to do so led to wasted effort.
- **Process Management Limitations:** Recognize the limitations of `exec` and `pty` for long-running, critical processes in dynamic environments (like Node.js dev servers). When stability is paramount, externalize process management to the user (manual terminal windows) or leverage robust process managers (e.g., `pm2`, `nodemon` with specific configs) if available and allowed.
- **Debugging Order:** Prioritize data accuracy (backend inference) before visual presentation (frontend styling). If the data is wrong, styling cannot correctly reflect it.
