# 2026-05-26 Daily Log - VAT Chat Bugfix & Dictation Mode Deployed

## Updates & Engineering Accomplishments
- **[RESOLVED] VAT Chat Textarea Display Bug**: Fully resolved the issue where nothing would display in the chat's message bar (textarea input) when using "press to submit" voice mode over non-localhost origins (e.g., laptop connecting via Tailscale).
  - **Root Cause & Discovery**: 
    1. Browsers restrict native `SpeechRecognition` in insecure (non-localhost, HTTP) contexts (such as Tailscale IPs). This forces VAT Chat to fallback entirely on the local FastAPI Whisper transcription server using real-time preview blobs (`/api/chat/stt-preview`).
    2. The preview generator in `useVAT.ts` used `previewChunksRef.current.slice(-12)` to construct periodic preview audio blobs (every 1400ms).
    3. Crucially, WebM/Ogg media streams generated by the browser's `MediaRecorder` pack container-level file and codec headers (EBML/segment details) strictly into the **very first chunk (index 0)**. 
    4. By slicing off the last 12 chunks, the first chunk was omitted, resulting in raw stream frames devoid of container headers. PyAV (which `faster-whisper` uses on the backend to decode audio files) was therefore unable to open the file, raising a persistent `av.error.InvalidDataError: [Errno 1094995529] Invalid data found when processing input` and returning 500 errors to the client. This kept the text input bar 100% empty.
    5. Additionally, strict guard checks in `ChatPopupV3.tsx` (`< 512` bytes and `< 256` bytes) would preemptively discard early voice packet previews.
  - **The Fix**: 
    1. Refactored `useVAT.ts` to construct `previewBlob` using the cumulative `chunksRef.current` array. Because it starts from index 0, the container headers are always present, making the files completely decodable by PyAV/FFmpeg on the backend. This also enables Whisper to transcribe the full growing sentence for superior accuracy.
    2. Lowered the minimum blob size checks inside `ChatPopupV3.tsx` from `512` and `256` bytes down to a defensive `64` bytes.
  - **HMR & Dev Server Recovery**:
    1. Noticed that the active dev server was running in default Turbopack mode, which suffers from silent WebSocket / HMR synchronization hangs when accessed remotely over Tailscale networks, causing code modifications to not be served to the browser.
    2. Gracefully terminated the old dev processes (PIDs 33528, 32828, etc.) and restarted the Next.js dev server with Webpack mapping strictly as mandated: `npx next dev --hostname 0.0.0.0 --webpack` (PID 50556).
